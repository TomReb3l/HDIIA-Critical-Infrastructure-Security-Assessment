# HDIIA Documentation Standard


# Ελληνική Έκδοση


## 1. Σκοπός Εγγράφου

Το παρόν έγγραφο καθορίζει τα πρότυπα δημιουργίας, δομής, παρουσίασης και διαχείρισης όλων των εγγράφων που αποτελούν μέρος του HDIIA Critical Infrastructure Security Assessment Project.

Στόχος είναι η διατήρηση:

- Επαγγελματικής συνέπειας
- Τεχνικής ακρίβειας
- Επιχειρησιακής συνάφειας
- Ελεγχόμενης τεκμηρίωσης

σε ολόκληρο το Security Documentation Framework.


---

# 2. Documentation Principles


## Business First

Όλες οι αναλύσεις ξεκινούν από:

- Επιχειρησιακές απαιτήσεις
- Κρίσιμες υπηρεσίες
- Επιχειρησιακές επιπτώσεις
- Απαιτήσεις διαθεσιμότητας και προστασίας

και όχι από συγκεκριμένα εργαλεία ή τεχνολογίες.


## Risk-Based Approach

Οι αποφάσεις ασφαλείας βασίζονται σε:

- Asset Criticality
- Threat Landscape
- Vulnerability Considerations
- Risk Level
- Business Impact


## Defense in Depth

Η προστασία σχεδιάζεται με πολλαπλά επίπεδα ελέγχων:

- Technical Controls
- Administrative Controls
- Physical Controls
- Human Controls


## Evidence Driven Documentation

Κάθε σημαντική απόφαση πρέπει να υποστηρίζεται από:

- Security Reasoning
- Risk Justification
- Security Objective
- Expected Outcome


---

# 3. Standard Document Structure

Κάθε security document ακολουθεί, όπου εφαρμόζεται, την παρακάτω δομή:


## Purpose

Περιγράφει:

- Γιατί δημιουργήθηκε το έγγραφο
- Ποιο πρόβλημα εξετάζει


## Business Context

Περιγράφει:

- Επιχειρησιακή σημασία
- Κρίσιμες υπηρεσίες
- Επιπτώσεις πιθανής αποτυχίας


## Scope

Καθορίζει:

- Τι περιλαμβάνεται
- Τι εξαιρείται


## Analysis

Περιλαμβάνει:

- Τεχνική ανάλυση
- Security considerations
- Threat considerations


## Risk Considerations

Περιγράφει:

- Αναγνωρισμένους κινδύνους
- Επιπτώσεις
- Προτεραιότητες


## Security Recommendations

Περιλαμβάνει:

- Προτεινόμενα Security Controls
- Βελτιώσεις
- Επόμενα βήματα


## Framework Alignment

Όπου εφαρμόζεται γίνεται αντιστοίχιση με:

- NIST Cybersecurity Framework
- NIST SP 800-53
- ISO/IEC 27001
- CIS Controls
- Zero Trust Principles


---

# 4. Document Classification

Όλα τα έγγραφα του project ταξινομούνται στις παρακάτω κατηγορίες:


## Governance Documents

Έγγραφα που καθορίζουν:

- Διαδικασίες
- Standards
- Methodology
- Project Rules


## Assessment Documents

Έγγραφα που περιλαμβάνουν:

- Current State Assessment
- Asset Analysis
- Threat Analysis
- Risk Assessment


## Architecture Documents

Έγγραφα που περιλαμβάνουν:

- Target Security Architecture
- Security Design Decisions
- Control Architecture


## Technical Analysis Documents

Έγγραφα που περιλαμβάνουν:

- Technical Security Analysis
- Security Controls
- Implementation Considerations


## Interview Preparation Documents

Έγγραφα που περιλαμβάνουν:

- Interview Questions
- Technical Explanations
- Decision Justification

Οι παρακάτω όροι παραμένουν στα Αγγλικά:

- Risk Assessment

- Security Controls

# 6. Writing Style

Η τεκμηρίωση πρέπει να είναι:

- Επαγγελματική
- Αντικειμενική
- Τεχνικά ακριβής
- Βασισμένη σε τεκμηρίωση


Αποφεύγονται:

- Marketing γλώσσα
- Υπερβολικοί ισχυρισμοί
- Μη τεκμηριωμένες υποθέσεις


---

# 7. Interview Preparation Principle

Κάθε σημαντική απόφαση πρέπει να μπορεί να υποστηριχθεί σε τεχνική συνέντευξη.

Η ανάλυση πρέπει να απαντά:

- Γιατί υπάρχει αυτός ο κίνδυνος;
- Ποιο Asset επηρεάζεται;
- Ποιο Security Control προτείνεται;
- Ποιο Risk μειώνει;
- Πώς αξιολογείται η αποτελεσματικότητά του;


---

# 8. Version Control Standards

Όλες οι αλλαγές διαχειρίζονται μέσω Git.

Κάθε αλλαγή πρέπει να περιλαμβάνει:

- Meaningful Commit Message
- Clear Documentation Update
- Review πριν το Commit


Παραδείγματα:

- Add asset criticality classification model
- Create threat actor analysis document
- Update security architecture recommendations

# English Version


## 1. Document Purpose

This document defines the standards for creating, structuring, presenting and managing all documentation included in the HDIIA Critical Infrastructure Security Assessment Project.

The objective is to maintain:

- Professional consistency
- Technical accuracy
- Business alignment
- Controlled documentation

throughout the Security Documentation Framework.


---

# 2. Documentation Principles


## Business First

Security analysis starts from:

- Business requirements
- Critical services
- Operational impact
- Availability and protection requirements

and not from specific tools or technologies.


## Risk-Based Approach

Security decisions are based on:

- Asset Criticality
- Threat Landscape
- Vulnerability Considerations
- Risk Level
- Business Impact


## Defense in Depth

Security protection is designed through multiple layers:

- Technical Controls
- Administrative Controls
- Physical Controls
- Human Controls


## Evidence Driven Documentation

Important decisions must be supported by:

- Security Reasoning
- Risk Justification
- Security Objectives
- Expected Outcomes


---

# 3. Standard Document Structure

Security documents should follow this structure where applicable:

- Purpose
- Business Context
- Scope
- Analysis
- Risk Considerations
- Security Recommendations
- Framework Alignment


---

# 4. Document Classification

Project documentation is classified into:

## Governance Documents

Standards, methodology and project rules.


## Assessment Documents

Current state analysis, assets, threats and risks.


## Architecture Documents

Security architecture and design decisions.


## Technical Analysis Documents

Technical security analysis and implementation considerations.


## Interview Preparation Documents

Technical explanations and decision justification.


---

# 5. Security Terminology

The project uses internationally recognized cybersecurity terminology.

The following terms remain in English:

- Security Assessment
- Threat Modeling
- Risk Assessment
- Security Architecture
- Security Governance
- Identity and Access Management (IAM)
- Security Controls
- Human Risk Management
- Security Awareness
- Data Center
- Critical Infrastructure


---

# 6. Writing Style

Documentation must be:

- Professional
- Objective
- Technically accurate
- Evidence-based


Avoid:

- Marketing language
- Unsupported claims
- Unverified assumptions


---

# 7. Interview Preparation Principle

Each important security decision must be defensible during technical interviews.

The analysis should answer:

- Why does this risk exist?
- Which asset is affected?
- Which security control is recommended?
- What risk is reduced?
- How is effectiveness evaluated?


---

# 8. Version Control Standards

All changes are managed through Git.

Each update should include:

- Meaningful commit message
- Clear documentation update
- Review before commit
